# Architecture

## Stack
- **Runtime:** Node.js + Express (`src/app.js`).
- **Database:** SQLite via `better-sqlite3` (WAL mode). One file, `tannins.db`.
- **Frontend:** Vanilla-JS PWA in `public/`, tablet-first, **no build step**. Each page is a
  self-contained `index.html` + its own stylesheet; shared logic lives in `public/theme.js`
  (an ES module imported by every page).
- **Auth:** HTTP Basic Auth (bcrypt) on admin routes only; server/cuisine views are public.
- **AI:** Anthropic Claude API, used only by seed scripts to generate pairing/flavor copy.
- **Hosting:** Render web service + 10 GB persistent disk mounted at `/data`.

## Multi-tenancy
A **tenant is a row in `restaurants`**, keyed by a URL `slug`. Everything is scoped by slug:

- **Routing** (`src/app.js`): `/:slug` (landing), `/:slug/server`, `/:slug/cuisine`,
  `/:slug/de` (admin). API routes are `/api/:slug/...`; `/api/beverages` is the one
  cross-tenant route (the shared catalog). The frontend reads the slug from
  `location.pathname.split('/')[1]`.
- **Per-tenant auth** (`src/auth.js`): `basicAuth` looks up the restaurant by slug and
  bcrypt-compares against *that restaurant's* `http_pass_hash`. Each tenant has its own
  admin credential.
- **Data isolation:** `wine_list`, `racks`, `menu_items` carry `restaurant_id`. **`beverages`
  is a global catalog** (no `restaurant_id`), matched by name and shared across tenants —
  see `data-model.md`.
- **Branding is data-driven per tenant:** `logo_image_path`, `theme_accent`, `theme_bg` on
  the restaurant row; uploads stored under `/data/uploads/{slug}/`.
- **Provisioning:** there is no create-restaurant API. New tenants are inserted via
  `scripts/create-tenant.js` (see `runbook.md`). Current tenants: `tannins-bar` (original),
  `mountain-prime` (first client — Mountain Prime Steakhouse & Lounge).

## Pages
- **Landing** (`public/landing/`) — three branding tiers: **Easily Paired** logo (global,
  top), the tenant's logo + name (middle, data-driven), **© Pariz LLC** (global, bottom).
  Links to the server and cuisine views.
- **Server** (`public/server/`) — floor-facing wine lookup by rack # or name; opens a detail
  modal per wine. No login.
- **Cuisine** (`public/cuisine/`) — dish-first: browse menu items, see paired wines (same
  detail modal). No login.
- **Admin** (`public/admin/`) — Basic-Auth panel: manage wines, prices, racks, menu items,
  pairings, logo/theme.

## Theming
Colors are CSS custom properties (`--bg`, `--surface`, `--text`, `--text-muted`, `--border`,
`--accent`, …) defined in each page's `:root`. `public/theme.js` `applyTheme(accent, bg)`
derives a full palette from the tenant's two colors and sets the variables **as inline styles
on `<html>`** — so per-tenant theme overrides the stylesheet defaults.

## High-contrast mode
An accessibility toggle (readability for low-vision users). `theme.js` exposes
`toggleContrast()` / `initContrastToggle(btnId)`, which flip a `data-contrast="high"`
attribute on `<html>` and persist the choice in `localStorage` (per device). A **"High
Contrast" button** sits in the server/cuisine/admin headers; the landing page respects the
setting but has no button.

Each stylesheet has a `:root[data-contrast="high"]` block that pushes muted greys to full
text color and keeps placeholders readable. It uses **`!important` targeting `var(--text)`**
— `!important` is required because `applyTheme` sets `--text-muted` inline (a normal
stylesheet rule would lose to the inline style), and `var(--text)` makes it adapt to any
tenant's light or dark theme. A tiny inline `<head>` snippet applies the saved setting before
first paint to avoid a flash.

## AI seeding
`beverages.general_pairing` and `beverages.flavor_profile` are generated by
`scripts/seed-enrich.js` and `scripts/seed-flavor.js` respectively (Claude API). Both are
incremental — they only fill rows that are null/empty, so they are safe to re-run. See
`runbook.md`.
